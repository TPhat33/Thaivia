# เหตุผลการเลือก candidate bbox พื้นที่ที่ 2 และ 3 (G6-02)

สถานะ: **ข้อเสนอ crop เท่านั้น ไม่ใช่รายงาน coverage** ยังไม่มีการ acquire
ข้อมูลจริงสำหรับทั้งสอง bbox นี้ (การ acquire ถูกบล็อกโดย egress policy
ของ environment นี้ — ดู ADR-0003) เอกสารนี้จึง **ไม่กล่าวอ้าง** ว่ามี
ถนน/อาคาร/คลองอะไรอยู่ในสอง bbox นี้จริง เป็นเพียงเหตุผลว่าทำไมจึงเลือก
crop นี้มาเป็น "candidate ที่ควรลองก่อน" เมื่อ network access กลับมาใช้ได้
(G6-03)

## หลักการเลือก

Plan §4 (`IMPLEMENTATION_PLAN.th.md`) กำหนดว่า 3 พื้นที่คือ **scope
ceiling** ไม่ใช่ quota — ถ้าคุณภาพข้อมูลของ candidate ใดไม่ผ่านหลังตรวจ
จริงใน G6-03 (topology conflicts มากเกินไป, feature เบาบางเกินจะเล่นได้,
ฯลฯ) ให้หยุดที่จำนวนน้อยกว่า 3 ได้ ไม่ใช่ความล้มเหลว

เกณฑ์เลือก bbox ทั้งสองนี้คือ **โจทย์ gameplay ที่ต่างจาก pilot** (พื้นที่
เดิม `th-bkk-pilot-001` ที่ crop รอบย่าน CBD ผสมสำนักงาน/ที่พักอาศัยหนาแน่น)
ไม่ใช่การเลือกเพราะ "รู้ว่ามีอะไรอยู่ในนั้นจริง" — ยังไม่รู้ ทั้งสอง
crop เลือกจากตำแหน่งภูมิศาสตร์กว้างๆ ของกรุงเทพฯ ที่รู้จักกันทั่วไป
(ย่านเมืองเก่าที่มีเครือข่ายคลอง กับ ย่านตลาด/สี่แยกที่มีถนนสายหลักตัดผ่าน)
ไม่ใช่จากการ trace แผนที่ใดๆ (ไม่ใช่ Google Maps/Street View — ต้องห้าม
ตาม AGENTS.md ข้อ 7)

## Candidate 2 — `th-bkk-candidate-002`

- bbox (WGS84 lon/lat): `[100.494, 13.754, 100.503, 13.763]`
- โจทย์ gameplay ที่ตั้งสมมติฐานไว้ (ต้องพิสูจน์หลัง acquire จริง):
  ย่านเมืองเก่าฝั่งที่คาดว่ามีเครือข่ายคลอง/ซอยแคบหนาแน่นกว่า pilot —
  ถ้าจริง จะทดสอบโจทย์ **canal-crossing accessibility** (ทางเชื่อมข้ามคลอง
  จำกัด, ระยะทางเครือข่ายสูงกว่าระยะตรงมาก) ซึ่งต่างจาก pilot ที่เป็น
  ย่านถนนสายหลัก/ตึกสำนักงานเป็นหลัก
- ทำไมถึงต่างจาก pilot: pilot bbox ไม่มีคลองสำคัญตัดผ่านที่ทราบ (ยังไม่
  ตรวจจริงเช่นกัน) การเลือก crop ที่คาดว่ามีคลองทำให้ระบบ utilities/
  accessibility ที่คำนวณจาก network graph (G6-06) มีโจทย์ที่ท้าทายกว่า
  รัศมีตรงเพียงอย่างเดียว

## Candidate 3 — `th-bkk-candidate-003`

- bbox (WGS84 lon/lat): `[100.553, 13.794, 100.562, 13.803]`
- โจทย์ gameplay ที่ตั้งสมมติฐานไว้ (ต้องพิสูจน์หลัง acquire จริง):
  ย่านที่คาดว่ามีถนนสายหลัก/สี่แยกและพื้นที่ตลาด/พาณิชย์หนาแน่นตัดผ่าน —
  ถ้าจริง จะทดสอบโจทย์ **arterial congestion + mixed-use noise** (ปริมาณ
  จราจรสายหลักสูง ผสมกับกิจกรรมพาณิชย์ที่มีเสียง/เวลาเปิดต่างจากย่าน
  สำนักงานของ pilot)
- ทำไมถึงต่างจาก pilot และ candidate 2: ให้ทั้งสามพื้นที่ครอบคลุมมิติ
  gameplay ที่ต่างกัน (office/residential mix, canal/old-town access,
  arterial/market congestion) แทนที่จะเป็น crop สามอันที่คล้ายกัน

## สิ่งที่ยังไม่รู้ / ยังไม่ทำ

- ไม่มีการยืนยัน feature ใดๆ ในสอง bbox นี้ — `coverage_status` ทั้งคู่
  เป็น `UNVERIFIED` พร้อมเหตุผลใน config เอง (`coverage_status_reason`)
- G6-03 (acquire จริง + `docs/data/pilot-audit-<area>.md` ต่อพื้นที่) ยัง
  `blocked` ใน `TASKS.json` — ต้องรอ network access ที่ไม่ถูกบล็อก หรือ
  ไฟล์ `.osm.pbf`/Overpass extract ที่มนุษย์ส่งมาให้แบบ offline
- ถ้าตรวจแล้วพบว่า bbox ใดข้อมูลเบาบางเกินไปหรือ topology มีปัญหามาก ให้
  ปรับ bbox โดยคง footprint จริง (ตาม plan §5) ไม่ใช่ลบทิ้งแล้วหา crop
  ใหม่แบบสุ่ม และถ้าคุณภาพไม่ผ่านทั้งคู่ การจบที่ 1 หรือ 2 พื้นที่แทน 3
  เป็นผลลัพธ์ที่ยอมรับได้ตาม scope ceiling
